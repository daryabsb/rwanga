## (c) Source-level finding — no forked layout model

Grepped `rwanga-editor/renderer/js/framework/layout-profile.js` and
`rwanga-editor/renderer/css/editor-prosemirror.css` for `rtl` near numeric geometry constants:

- **`layout-profile.js:64-92`** (`HOLLYWOOD_DEFAULTS.blockWidthsIn`, `leadingBlankLines`) — **one** table
  of column widths (character 3.5in, dialogue 2.5in, parenthetical 2.0in, others 6.0in). No
  direction-keyed variant exists anywhere in this object.
- **`editor-prosemirror.css:2484-2519`** (`.rga-print-block-character/parenthetical/dialogue/transition`)
  — **one** set of numeric values (`padding-inline-start: 2.0in / 1.5in / 1.0in`; `text-align: end`),
  expressed in **logical** properties. There is no `[dir="rtl"] { padding-inline-start: <different
  number> }` override anywhere in the file — the only `[dir="rtl"]` selectors present
  (`editor-prosemirror.css:873-874`, `2008`, `2081`, `2362`, `2564`, `2598-2599`) touch **font-family**,
  a scene-number/heading class name, and icon mirroring — never a geometry magnitude.
- **Verdict: no forked layout model. No RTL-only geometry constant exists in the resolver.** The single
  `blockWidthsIn` table + logical CSS properties are the entire mechanism; direction only selects which
  physical edge `padding-inline-start`/`text-align: end` resolve to (browser-native bidi/logical-property
  behavior), which is exactly Law 12 ("one resolver, two directions").

**Two direction-aware exceptions found, and neither is a violation:**

1. **`layout-profile.js:102-108` (`RTL_PRINT_LEADING = 1.3`)** — a direction-keyed **leading** value
   (LTR 1.0 / RTL 1.3), explicitly documented in the source as "Print Truth Unification V1, SCOPE B" and
   grounded in `RTL_SCREENPLAY_CONVENTION.md §6`, the ratified "one deliberate typographic relaxation."
   This is vertical rhythm, not horizontal geometry — the convention itself carves out this single
   exception. **Not a violation.**
2. **`layout-profile.js:117-131` (`_charsPerInch`, `baseCpi = (direction === 'rtl') ? 14.5 : 10`)** — a
   direction-keyed **characters-per-inch** constant used only for `cpl` (pagination budget), sourced from
   a measured Noto Naskh Arabic glyph-capacity forensic (comment cites Density Slice 4/7). This affects
   how many characters of a **given font** fit in the fixed-inch column width — it does not change any
   column's **width in inches**. The 2.0in / 1.5in / 1.0in / 3.5in magnitudes above are untouched; this
   is a font-metric input to line-wrapping, not a second geometry model. **Not a violation**, but worth
   naming explicitly since it is the one place `direction` feeds a number outside the leading exception.

## (d) Vocabulary / localisation observations (carried from RTL-08, RTL-12)

- **Transitions render the English `CUT`, not a localized Kurdish/Arabic equivalent** (e.g. `قطع`).
  Per the S4.1 protocol this is a vocabulary matter, not a geometry defect — RTL-08 passes on alignment.
  **Not ticketed as a gap**: the convention's vocabulary layer (`doc.settings.vocabulary`) already
  localizes `INT./EXT.`/time-of-day/scene-word in the fixture; transitions are simply not yet wired to
  that same table. This is real, minor, product-visible scope — recording it here for whoever picks up
  vocabulary completeness, but it does not block SW-23 because the convention explicitly separates
  geometry (law) from vocabulary (translation layer), and RTL-08's geometry is TRUE.
- **Numerals: the fixture renders Eastern-Arabic digits (`٣`, `٨`, `٢`, `١`) even though the convention's
  documented default is Western-Arabic (0–9) with Eastern-Arabic as an opt-in locale setting.** S4.4
  confirmed this is the **document's own authored content** (the fixture's Kurdish prose freely mixes
  both systems), not an app-enforced default — there is no evidence the app fails to honor a Western
  default; there is simply no probe in this Phase that opens a *fresh* document and confirms numerals
  default to Western-Arabic absent authored digits. **Recorded, not ticketed as a gap**: this is a
  locale-default verification gap, distinct from a known defect, and belongs to whichever future slice
  does a vocabulary/locale-settings audit — it does not block SW-23 because RTL-12's own base-direction
  and readability criteria (the only geometry/rendering claims RTL-12 makes) are TRUE regardless of
  which numeral system the source text used.

## Final SW-23 verdict

**SW-23 = PARTIAL.**

All three of SW-23's structural requirements are met:
- (a) RTL-04, 05, 06, 07, 08, 09, 10, 12, 13 = TRUE (9 of 11 sub-checks)
- (b) the profile flip proves one resolver, two directions, identical magnitudes (decisive test, above)
- (c) no forked layout model; the two direction-aware exceptions found are both ratified, non-geometry
  deviations (leading + font-metric cpi), not violations
- (d) vocabulary/localisation observations recorded, none silently absorbed

**The single thing holding SW-23 at PARTIAL rather than TRUE is RTL-11**, which itself is PARTIAL: PDF
export renders the RTL document correctly (same page count as Preview, real Arabic-script characters,
zero replacement/tofu glyphs) but **~40.2% of the exported PDF's Kurdish text has no `ToUnicode` mapping**
(35,749 of ~88,928 script characters extract as NUL) — **GAP-4-1**. This breaks copy/paste, text search,
screen-reader access, and any downstream tooling (breakdown software, festival portals, archive indexing)
that reads the PDF as text, even though the printed page is visually correct. Per the masterplan's
escalation rule (§0.2), a real defect measured at this magnitude is not something a Phase-4 QA slice may
paper over by flipping RTL-11 or SW-23 to TRUE.

**Proposed checklist row text** (for the orchestrator to apply in
`docs/RWANGA_IDE_LAUNCH_CHECKLIST.md`; this agent did not edit that file):

> **SW-23 — RTL screenplay convention support: PARTIAL.** The RTL profile drives the convention via a
> single logical-property resolver (no forked layout model) — verified by RTL-04…10, 12, 13 (all TRUE)
> and by the decisive profile-flip test (flipping `screenplayProfile.direction` to `ltr` on a fixture
> copy reproduces the identical 2.0in/1.5in/1.0in magnitudes mirrored to the opposite edge; a brand-new
> RTL document reproduces them with zero manual tweaking). Held at PARTIAL solely by **RTL-11 (PDF export
> text layer)**, itself PARTIAL: the exported PDF renders correctly but ~40% of its Kurdish text has no
> Unicode mapping (**GAP-4-1**, open). Localized-transition vocabulary and default-numeral-system are
> recorded observations for a future vocabulary/locale slice, not launch-blocking geometry defects.
> Evidence: `docs/plans/evidence/S4.1-rtl-qa-protocol.md`, `S4.2-rtl-alignment.md`,
> `S4.3-rtl-print-pdf.md`, `S4.4-bidi-audit.md`, `S4.5-sw23-verdict.md`.
