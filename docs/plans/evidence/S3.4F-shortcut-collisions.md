# S3.4F — GAP-3-5 fix: keyboard-shortcut collisions

- **Date:** 2026-07-29
- **HEAD (before this slice's changes):** `04bdd4409272ec93a90f49007eed3a6cef1b75c6` (branch `main`, clean)
- **Source audit:** `docs/plans/evidence/S3.3-console-audit.md`
- **User ruling (2026-07-29, binding):** `Ctrl+Shift+S` belongs to Save As, permanently. Scene
  Navigator must move.

## The three collisions, before → after

| Command | Old default | New default | Why |
|---|---|---|---|
| `kb.saveAs` (Save As) | `Ctrl+Shift+S` | `Ctrl+Shift+S` (**unchanged**) | User ruling: the near-universal Save As binding (Word, Photoshop, VS Code); writers reach for it by muscle memory. |
| `kb.sceneNavigator` (Scene Navigator panel) | `Ctrl+Shift+S` | `Ctrl+Shift+1` | Collided with `kb.saveAs`; Scene Navigator registered last in the kb-applicator's boot loop and silently won, so Save As never fired. `Ctrl+Shift+1` is not a new invention — `renderer/js/shell/index.js`'s hardcoded `_PANEL_SHORTCUTS` table already binds `panel.sceneNavigator` to Ctrl+Shift+1 (a leftover of the earlier §A4.1 recovery). Settings' *displayed* default had simply never been updated to match. This fix makes Settings honest, not just collision-free. |
| `kb.exportPdf` (Export PDF) | `Ctrl+Shift+E` | `Ctrl+Alt+E` | Collided with the shell's hardcoded `scriptWorkspace` panel-toggle (also Ctrl+Shift+E); the Settings-driven kb-applicator layer registers last at boot, so Export PDF silently won and the panel toggle stopped firing. Alt-modifier space was entirely unused elsewhere in the registry, so Ctrl+Alt+E is collision-free by construction; it keeps the "E" mnemonic and is not a well-known OS/browser/editor binding. |
| `search` panel toggle (shell-hardcoded, no Settings entry) | `Ctrl+Shift+F` | `Ctrl+Shift+2` | Collided with `editor/js/editor/shortcuts.js`'s legacy annotation shim ("flag for revision"), which is functional and registers *after* the panel table, so it was the one actually winning — the search panel's own declared shortcut never fired even before this fix. Moved off F rather than touching the working flag-for-revision shortcut. `Ctrl+Shift+2` follows the same VS-Code-style numbered-panel convention already established for Scene Navigator (`Ctrl+Shift+1`). The search panel is currently `available: false` (placeholder), so no working feature was disrupted by the move; its `shortcut` display label in `renderer/js/shell/panels/search.js` was updated to `Cmd-Shift-2` to match. |

A fourth, related-but-separate stale spot found while doing this fix: `renderer/index.html`'s
`file.exportPdf` menu command carried a hardcoded `displayAccelerator: 'Ctrl+Shift+E'` string (the
menu's own display channel for a command whose real key binding lives in the Settings-driven
`export.pdf` command). Left unchanged, the menu would have started lying about Export PDF's
shortcut the moment `kb.exportPdf`'s default moved. Updated to `'Ctrl+Alt+E'` in the same commit —
this is the Settings-honesty principle applied to the *menu*, not just the Settings screen.

## How the guard works (Step 1)

`rwanga-editor/tests/unit/shell/kb-shortcut-default-collisions.test.js`, 6 tests:

1. **Generic sweep #1** — loads the REAL `Rga.Settings.Registry` (via `settings-validators.js` +
   `settings-registry.js`, executed in jsdom, not re-typed) and asserts no two `type: 'shortcut'`
   entries share a default combo. This alone catches the `kb.saveAs` / `kb.sceneNavigator`
   collision.
2. **Generic sweep #2** — cross-checks every `kb.*` default against `shell/index.js`'s hardcoded
   `_PANEL_SHORTCUTS` table (parsed from source text — the same static-parsing technique
   `tests/unit/shell/owned-chrome-A4.1-accelerator-ownership.test.js` already uses for `MENU_DEFS`,
   so this isn't a new pattern in the codebase). An explicit one-line allowlist recognises
   `kb.sceneNavigator` ↔ `panel.sceneNavigator` as the SAME feature (Settings honestly re-displaying
   the shell's real binding), so that intentional match isn't flagged as a false collision. This
   catches the `kb.exportPdf` / `scriptWorkspace` collision.
3. **Targeted check** — parses `editor/shortcuts.js`'s legacy shim registrations and asserts the
   `search` panel's real combo doesn't collide with them. Catches the `Ctrl+Shift+F` collision.
4. **Three regression pins** — `kb.saveAs` stays `Ctrl+Shift+S`; `kb.sceneNavigator`'s default
   equals the shell's real `Ctrl+Shift+1` binding (parsed, not hardcoded, so it can't silently
   drift again); `kb.exportPdf` no longer equals the scriptWorkspace panel's combo.

All 6 were run and **confirmed RED** against the pre-fix source (git history / by construction —
watched fail with the exact three collisions before any source change was made), then confirmed
GREEN after the two settings-registry.js edits and the `_PANEL_SHORTCUTS` edit. This is a standing
guard: a future contributor who adds a colliding `kb.*` default, or reintroduces a colliding
`_PANEL_SHORTCUTS` entry, fails this test — in the registry, not the console.

**Deliberately out of the guard's scope** — see "Proposed gap rows" below: `Ctrl+Shift+T` is ALSO
claimed by both `kb.toggleTheme` and `editor/shortcuts.js`'s legacy "tag as" shim. The S3.3 audit
did not escalate it into GAP-3-5 and this slice's ledger names only the three collisions above, so
the guard does not assert on it (asserting on it would fail today and require an out-of-ledger fix
to go green — scope discipline, not an oversight).

## Step 4 — end-to-end proof (Save As fires; Settings tells the truth)

`rwanga-editor/tests/e2e/settings/gap-3-5-shortcut-collisions.spec.js`, 4 tests, run against a
real launched Electron app (no mocking of `Rga.KeyboardRegistry` — real `Ctrl`/`Shift`/`Alt`
keypresses via Playwright's `page.keyboard`):

1. **Settings honesty** — opens the Settings → Shortcuts section and reads the rendered key caps
   for `kb.saveAs`, `kb.sceneNavigator`, `kb.exportPdf`. Confirms `['Ctrl','Shift','S']`,
   `['Ctrl','Shift','1']`, `['Ctrl','Alt','E']` respectively — Settings displays exactly what now
   really fires.
2. **Save As fires on Ctrl+Shift+S, Scene Navigator does not.** Scene Navigator is the
   screenplay doc-type's default sidebar panel, so it's already current + visible at boot; the
   proof that its toggle did NOT also fire is that this state is byte-for-byte unchanged after the
   keypress (if it had fired, `_togglePanel` would have deactivated it, since it was already
   current+visible — the exact failure mode of the pre-fix bug). Meanwhile the REAL
   `Rga.FileManager.saveAs` (monkey-patched only to count calls, still delegating to the original)
   is confirmed invoked. The native save dialog is stubbed (`canceled: true`) so nothing is written
   to disk.
3. **Ctrl+Shift+1 activates Scene Navigator** — its new, honestly-advertised default really works:
   switches away to `scriptWorkspace` first, presses the combo, confirms Scene Navigator becomes
   current.
4. **Ctrl+Alt+E fires Export PDF; the OLD default (Ctrl+Shift+E) now belongs solely to the
   scriptWorkspace panel and no longer reaches Export PDF at all** — presses the pre-fix combo
   first and confirms it toggles `scriptWorkspace` with zero `Rga.PdfExport.run` calls, then
   presses the new combo and confirms `Rga.PdfExport.run` fires (real export pipeline; the
   main-process `dialog.showSaveDialog` is stubbed to `canceled: true` so nothing is written).

All 4 pass. **Yes — Save As now actually fires on Ctrl+Shift+S in a running app, and Settings
displays the true binding for every affected command.**

## Proposed gap rows (found, not fixed — scope discipline)

1. **`Ctrl+Shift+T` collision (structurally identical to the fixed bugs, NOT in GAP-3-5's
   ledger).** `kb.toggleTheme`'s Settings default (`Ctrl+Shift+T`) and
   `editor/js/editor/shortcuts.js`'s legacy "tag as…" shim both claim `Ctrl+Shift+T`. At boot the
   kb-applicator wins (Toggle Theme fires), so the legacy shim's Ctrl+Shift+T "tag as" binding is
   dead on arrival — the same class of defect as the three fixed here. The S3.3 audit classified
   this pair as "benign layering" and did not escalate it into GAP-3-5, and this slice's ledger
   names only the three collisions fixed above, so it is reported here, not fixed. Tag-as has an
   alternative entry point (right-click → Tag as…), which likely explains the lower severity
   judgement, but the keyboard path is genuinely dead and Settings' `kb.toggleTheme` row does not
   disclose that a second feature is silently losing the same key.
2. **Electron insecure-CSP development warning** — already flagged by the S3.3 audit and
   explicitly out of scope for this slice per the task brief; not touched here, needs its own
   hardening slice.
