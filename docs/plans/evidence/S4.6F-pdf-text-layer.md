# S4.6F — GAP-4-1 diagnosis: the Kurdish PDF text-layer NUL defect

- **Date:** 2026-07-29 · **HEAD:** `99301c22` · **Branch:** `main`
- **Method:** `superpowers:systematic-debugging` — minimal one-paragraph repro, then a
  font-vs-pipeline bisect, then a per-character isolation experiment, all run **outside**
  the product (a standalone Electron harness in `%TEMP%`, product code untouched).
- **Baseline this builds on:** `docs/plans/evidence/S4.3-rtl-print-pdf.md` — 85-page fixture,
  35,749 NUL chars = **40.2%** of script characters.
- **This step is diagnosis-only.** No product code was modified, nothing was committed.

---

## 1. Minimal repro

A standalone harness (not the product) that does exactly what
`electron/bridge/export-pdf.js` does — load an HTML file in a hidden `BrowserWindow`, await
`document.fonts.ready`, call `webContents.printToPDF()` with the same option shape as
`electron/lib/pdf-print-options.js` — run against **one or two Kurdish sentences** instead of
the 85-page fixture.

```
# harness (scratch dir, not in the repo):
#   main.js   — Electron main process: loadFile(html) → fonts.ready → printToPDF → write buffer
#   gen.js    — writes one HTML file per experiment
#   analyze.js — pdf-parse extraction using the SAME regexes as
#                tests/e2e/rtl/rtl-print-export.spec.js (nulShareOfScriptChars)
electron.exe main.js <experiment>.html <experiment>.pdf '{}'
node analyze.js <experiment>.pdf
```

Test sentences were pulled from the **parsed JSON of the tracked fixture**
(`mysterious-guest-rtl.rga`, read via a `%TEMP%` copy, never modified), not retyped by hand:

```
نالی لەسەر جێگاکەی بە قووڵی خەوتووە، وەکو ئاگای لە هیچ شتێک نەبێت.
نالی بەرەو ناوەوەی ماڵەکە دەچێت، خەریکی قسەکردنە بە مۆبایلەکەی.
```

This reproduces the defect at paragraph scale in under 5 seconds per run, vs. minutes for the
85-page fixture, and gives the exact same extraction metric (`nulShareOfScriptChars`) used in
the S4.3 evidence.

## 2. Bisect table (paragraph scale)

| # | Experiment | Font | NUL share of script chars | What it rules in/out |
|---|---|---|---|---|
| 1 | Shipped path, 2 real Kurdish sentences | vendored **Noto Naskh Arabic** (`renderer/fonts/NotoNaskhArabic-Regular.woff2`) | **37.4%** | Reproduces the S4.3 defect (40.2%) at paragraph scale — confirmed minimal repro. |
| 2 | Same sentences, different vendored font | vendored **Noto Sans Arabic** | **38.1%** | Swapping to the *other* vendored Google-Noto family does **not** move the number — rules out "just this one font file is a bad build" as the whole story. |
| 3 | Same sentences | **Tahoma** (Windows system font) | **20.4%** | Switching families **roughly halves** the NUL share. Font matters. |
| 4 | Same sentences | **Arial** (Windows system font) | **20.4%** (byte-identical extraction to #3) | Confirms #3 — two independent system fonts land on the same number, i.e. it's not font-specific noise. |
| 5 | Latin control, identical pipeline | Noto Naskh Arabic declared, Latin text rendered | **0%** (0 NUL / 0 Arabic chars — clean) | **Anchors the bisect**: the identical `printToPDF` pipeline produces a perfectly clean text layer for non-Arabic script. | 6 | Same sentence, **ZWNJ-isolated** (every letter forced to isolated form, joining broken) | Noto Naskh Arabic | **19.2%** | Isolating the letters (removing contextual medial/final/ligature shaping) **cuts the NUL share roughly in half** vs. the same font shaped normally (#7). |
| 7 | Same sentence, normal shaping (paired control for #6) | Noto Naskh Arabic | **40.3%** | Confirms shaped/joined forms carry far more of the defect than isolated forms, in the same font. |

**Read together:** font swap alone (#1→#3/#4, same shaped text) roughly halves the defect.
Shaping alone (#6→#7, same font) also roughly halves it. Both levers move the number
independently, which is the signature of two compounding causes rather than one — resolved
by experiment 3 below.

## 3. Per-character isolation (the decisive experiment)

Every Arabic/Kurdish-script character used in the two test sentences (22 distinct code
points) was rendered **alone, in isolated form, one per PDF**, in both Noto Naskh Arabic and
Tahoma, then text-extracted individually:

| Outcome (isolated single glyph) | Noto Naskh Arabic | Tahoma |
|---|---|---|
| Extracts as the **NUL byte** | **9 / 21** tested (`ن ج گ ب ق خ ت چ ش` — every letter whose isolated glyph carries a dot mark) | **0 / 21** |
| Extracts as the **wrong character** (no NUL, but not the input glyph) | 4 / 21 (`ی→ى`, `ێ→ٚى`, `ڵ→ٚل`, `ئ→ٔى` — letters whose isolated glyph carries a diacritic mark: hamza / small-yeh / small-v) | 0 / 21 |
| Extracts **correctly** | 8 / 21 (dot-less/mark-less letters: `ل ر س و ه ، ک ە`) | 21 / 21 |

(One Noto Naskh single-character PDF, bare `ا` alone, produced a corrupt/unreadable PDF on
both runs — a harness artefact of a near-empty page, not investigated further; excluded from
the counts above and immaterial to the conclusion.)

**This is the decisive result.** Rendered in true isolation — no shaping, no neighbours, no
ligatures — **every Noto Naskh Arabic glyph that has a dot or diacritic mark loses or corrupts
its Unicode mapping**, while the identical characters in Tahoma map perfectly, 21/21. Since the
Chromium build, the `printToPDF` options, and the surrounding HTML/CSS pipeline are byte-identical
between these two runs, the variable that flips the outcome is **the font file** — this is font,
not pipeline, full stop.

The pattern also explains the residual gap: Noto Naskh Arabic evidently draws the "dot" and
"diacritic" components of many Arabic-script letters as **separate mark glyphs** (a common
Arabic-font technique: a base "rasm" skeleton glyph plus positioned combining-mark glyphs for
the dots), and Chromium's PDF subsetter either omits a `ToUnicode` entry for those mark glyphs
entirely (→ NUL) or maps them to an unrelated combining-mark code point (→ wrong character,
e.g. `ٔ` ARABIC HAMZA ABOVE, `ٚ` ARABIC SMALL HIGH YEH). Tahoma/Arial do not exhibit this because
their glyph outlines are monolithic (no separate mark decomposition for the isolated forms
tested).

The **second, smaller** cause — the residual ~20% NUL that persists even with Tahoma/Arial on
full shaped sentences (bisect row #3/#4) despite 0% on isolated single letters — is shaping
context: e.g. `ە` (U+06D5, the Kurdish/Sorani "e") extracts cleanly alone but becomes NUL when
medial-joined between `ل` and `س` in `لەسەر`, in **both** Tahoma and Noto Naskh. This shows
Chromium's `ToUnicode` CMap generation also loses some contextual/positional glyph variants
(the medial-form glyph selected by the shaping engine) independent of which font is used —
a smaller, pipeline-adjacent contribution, but clearly secondary: it accounts for ~20 points of
the 40% baseline, the font accounts for the other ~20, and they compound.

## 4. Named root cause

**Primary root cause (font):** the vendored **Noto Naskh Arabic** webfont
(`rwanga-editor/renderer/fonts/NotoNaskhArabic-Regular.woff2` and its Medium/SemiBold/Bold
siblings, declared in `renderer/css/tokens.css:32-53`) uses a glyph architecture where many
Arabic-script letters' dot and diacritic marks are separate combining-mark glyphs rather than
part of a single monolithic outline. When Chromium's PDF font subsetter
(`webContents.printToPDF`, invoked from `electron/bridge/export-pdf.js:67`) writes the
embedded subset's `ToUnicode` CMap, it fails to assign a correct code point to those mark
glyphs — most emit **NUL**, a smaller number emit an unrelated combining-mark code point. This
alone accounts for roughly half of the 40.2% baseline (bisect rows #1 vs #3/#4, and the 9-of-21
isolated dotted letters that break in Noto Naskh vs. 0-of-21 in Tahoma).

**Secondary, compounding root cause (font-independent, pipeline-adjacent):** Chromium's
`ToUnicode` CMap generation also drops the mapping for certain contextually-shaped
(medial/final) glyph variants regardless of font — demonstrated by `ە` (U+06D5) failing in a
joined word in **both** Noto Naskh Arabic and Tahoma/Arial, while succeeding for all fonts when
isolated. This accounts for the remaining portion of the baseline and is why even the
best system font tested still shows ~20% NUL on real shaped sentences, not 0%.

**Evidence anchors:**
- Font asset: `rwanga-editor/renderer/fonts/NotoNaskhArabic-Regular.woff2` (+ Medium/SemiBold/Bold), declared `rwanga-editor/renderer/css/tokens.css:32-53`.
- Code path: `rwanga-editor/electron/bridge/export-pdf.js:67` (`win.webContents.printToPDF(printOptions)`), options built by `rwanga-editor/electron/lib/pdf-print-options.js`.
- Extraction method matched to the standing test: `rwanga-editor/tests/e2e/rtl/rtl-print-export.spec.js` (`nulShareOfScriptChars`, lines ~270-276).
- Latin control (bisect #5) proves the `printToPDF` options themselves are not misconfigured — the identical options produce a perfectly clean text layer for Latin script.

## 5. Which lever fixes it — recommendation and risk

**Primary lever: change the font.** The font is the dominant, most fixable cause (roughly half
the defect, and the only cause visible even in fully isolated, unshaped glyphs — an
irreducible per-glyph property of the font file, not a runtime condition). Two directions worth
evaluating in the fix slice, in order of preference:

1. **Swap the vendored Arabic/Kurdish font for a build whose glyphs do not decompose dots into
   separate mark glyphs** (e.g. a font engineered for legacy/robust text extraction — some Noto
   Naskh Arabic *hinted/unhinted* build variants differ here, or an alternative Kurdish-capable
   Naskh/Arabic font with monolithic glyph outlines, as this experiment's Tahoma/Arial control
   demonstrates is achievable). **Risk:** changing the shipped font changes visual rendering
   (the RTL print/flow visual work already locked in prior slices was tuned against Noto Naskh
   Arabic's specific metrics — a font swap risks reopening RTL-10's leading/margin
   measurements and would need the same 85-page visual re-verification).
2. **Patch/repair the existing font's `cmap`/mark-glyph metadata** (e.g. with a font-engineering
   tool) so isolated dot/diacritic mark glyphs carry a correct Unicode assignment before
   Chromium subsets it. **Risk:** lower visual risk (same font, same metrics) but requires
   font-engineering expertise/tooling not currently in this repo, and does not touch the
   secondary (shaping-context) cause.

**Secondary lever, if pursued:** a post-export **PDF text-layer repair pass** (rewrite the
`ToUnicode` CMap of the produced PDF, or overlay a hidden, correctly-encoded text layer)
would address both causes independent of font choice, at the cost of a new post-processing
step in the export pipeline (`export-pdf.js`) and a new dependency for PDF manipulation.

**Rejected for this diagnosis:** changing `printToPDF` options (margins, `preferCSSPageSize`,
etc.) — bisect #5 (Latin control, identical options) already proves the options are not the
cause; varying them further would not have separated font from pipeline and was not pursued
once the Latin control and per-character results made the font the clear dominant lever.

**Not recommended:** trying to fix this by changing HTML/CSS only (e.g. `unicode-range`,
`font-feature-settings`) — the defect is in the font's own glyph→mark decomposition and
Chromium's CMap writer, neither of which is reachable from page-level CSS.

## 6. What remains UNKNOWN

- **Whether a differently-built Noto Naskh Arabic (different hinting/version) avoids the mark
  decomposition** — not tested; only the two fonts already vendored in this repo (Naskh, Sans)
  were compared, and both showed the same defect class. A wider font survey belongs to the fix
  slice.
- **The exact mechanism of the secondary (shaping-context) cause** — confirmed to exist and to
  be font-independent (fails in both Noto Naskh and Tahoma/Arial for medial `ە`), but *why*
  Chromium's CMap writer drops that specific glyph variant was not traced inside Chromium's
  source; only its existence and rough magnitude (~20 points of the 40%) were established by
  experiment.
- **Whether font-patching (lever 2) is practically achievable** with tools available to this
  team — not attempted; this diagnosis only establishes that the font, not the pipeline, is
  the primary lever.
- **The single bare-alef (`ا`) isolated PDF was corrupt/unparseable** on two runs — a minor
  harness artefact (likely a near-empty single-glyph page), not investigated further as it did
  not change the conclusion (7 other mark-less letters extracted cleanly in the same font).
