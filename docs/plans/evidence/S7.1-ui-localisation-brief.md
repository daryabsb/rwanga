## 1. The two-axis model

**UI direction** and **document direction** are kept apart by giving each exactly one writer and one
target element, and by construction (not just discipline) they cannot collide.

### The seam: the shell-root direction boundary

- **UI direction's only writer:** the new `language` applicator (S7.2), and **only** it, may set
  `document.documentElement.dir` and `document.documentElement.lang`. Nothing else in the codebase
  may touch `documentElement.dir` — this becomes the S7.3 source-guard's job to enforce (see §3 of
  the masterplan's S7.3, and the test shape in §6 below: a grep-based guard failing CI if a second
  `documentElement.setAttribute('dir'` call-site appears anywhere in `renderer/js/`).
- **Document direction's only writers:** the five existing call sites, unchanged, each still setting
  `dir` on its own subtree root (the editor host `<div>`, the print `<sheet>`, the scene-navigator
  wrapper, the tags wrapper, the review bar). They stay exactly as they are — S7.2/S7.3 must not
  touch them.
- **Why this can't conflict, structurally:** CSS `direction` inherits down the tree, but an explicit
  `dir` *attribute* on a descendant re-establishes direction for that subtree regardless of what the
  ancestor (including `<html>`) says. Because all five document-direction sites already set `dir`
  explicitly on their own root element (never relying on inherited `documentElement` direction), a
  Kurdish document already renders RTL today even though `<html>` is stuck at `ltr` — that is *why*
  the page content is already correct while the chrome is not (S4.2/S4.3 findings). Flipping
  `documentElement.dir` in S7.2 changes only the chrome that has no closer explicit `dir` ancestor —
  which is exactly and only the chrome. No document-direction site needs to change for S7.2 to be
  safe; that is the whole point of the seam.
- **The one thing S7.2 must add defensively:** a Playwright matrix (already scoped in the S7.2 step
  list) proving this holds in practice for all four combinations, because the *risk* is a future
  regression — someone reading `documentElement.dir` from inside a document-rendering path instead
  of computing direction from the script profile. The guard test in §6 (RTL-17) exists to catch that
  class of regression permanently, not just prove it once.

### Rejected alternative

CSS custom property (`--ui-dir`) toggled on `:root` and consumed via `[dir]`-style selectors
everywhere, instead of the native `dir` attribute. Rejected: the native attribute already gets free,
correct, automatic behaviour from the browser's bidi algorithm and from every third-party control
(`<select>`, `<input>`, scrollbars) with zero CSS to write; a custom property would require manually
reproducing that for every element and cannot override native form-control mirroring at all. There is
no scenario in this codebase where the native cascade is the wrong tool.

## 2. The translation layer

### One-paragraph shape

Plain JSON catalogues, one file per locale, at `renderer/locales/{en,ku,ar}.json`. Dot-namespaced
keys mirroring module structure (`shell.tabBar.recoverPrompt`, `settings.language.label`). A small
synchronous module `renderer/js/shell/i18n.js` (`Rga.I18n`) loads all locale JSON eagerly at shell
boot (files are tens of KB at most — no async fetch waterfall, no lazy loading, no CDN, matches the
"local assets only" and "no heavy dependency" constraints exactly). Lookup is `Rga.I18n.t(key, params)`,
synchronous, following the existing `Rga.*` singleton-module pattern already used throughout
`renderer/js/shell/` (e.g. `Rga.Settings.Applicators`, `Rga.KeyboardRegistry`).

### Decisions, with rationale

**Catalogue format — flat-namespaced JSON, not nested JSON, not `.po`/gettext, not ICU.**
- *Rejected: nested JSON* (`{shell: {tabBar: {recoverPrompt: "..."}}}`). Nesting reads nicer but
  diffs worse — adding one key touches brace structure above it, and merge conflicts between two
  slices editing the same nesting level (likely between S7.5/S7.6 translating in parallel) become
  structural instead of line-local. Flat keys (`"shell.tabBar.recoverPrompt": "..."`) keep every
  addition a one-line diff, which is exactly what the masterplan says a reviewer must see for S7.4
  (§3, "no big-bang rewrite").
- *Rejected: gettext `.po`/`.mo`.* Standard tooling for exactly this problem, but it pulls in a
  parser/compiler toolchain (or a hand-rolled one, which is worse) for a codebase that currently has
  zero build-time i18n tooling and a hard no-heavy-dependency constraint. JSON needs nothing: it is
  `require()`-able (Electron main/preload) or `fetch()`-able (renderer), and diffable with plain git.
- *Rejected: ICU MessageFormat.* Handles plurals/genders/interpolation uniformly and well, but is a
  real dependency (`@formatjs/intl` or similar) with a parser and runtime cost, for a UI surface that
  — per the §0 recount — is on the order of 60–100 short imperative strings, not a document-scale
  translation corpus. Proportionate tooling: see the plural/interpolation decisions below, which
  cover this surface's actual needs without ICU.

**Key naming convention:** `<owning-module-or-surface>.<local-name>`, lower-camel local segments,
dot-separated, e.g. `shell.statusBar.wordCount`, `settings.language.description`,
`dialog.recoverUnsaved.title`. Settings-registry entries use `settings.<entry.id>.label` /
`settings.<entry.id>.description` (see the registry-labels decision below) so a key is always
traceable back to the file that would have owned the literal.

**Lookup API surface:**
```
Rga.I18n.t(key, params)         // -> string. params: {name: 'Layla'} for {name} interpolation.
Rga.I18n.setLocale(code)        // -> swaps active catalogue, fires 'localechange'
Rga.I18n.getLocale()            // -> current code
Rga.I18n.on('localechange', fn) // -> subscribe for live re-render (see §5)
Rga.I18n.missingKeys()          // -> array, dev/test introspection (see below)
```
This mirrors the existing `Rga.Settings.Applicators` / `Rga.KeyboardRegistry` register/subscribe
shape already in the codebase — a developer who knows one `Rga.*` module already knows this one.

**Interpolation:** `{name}`-style placeholder, literal string replace, no plural/gender grammar
inside the placeholder syntax itself (that's handled by the separate plural key below). No format
functions (dates/numbers) are in scope for v1 — the audit's inventory is UI chrome strings, not
data formatting; if a formatted-number/date string turns up during S7.4 extraction, it gets flagged
as an open question then, not solved speculatively here.

**Pluralisation — two-form CLDR-lite (`_one` / `_other` key suffixes), not full CLDR plural rules.**
English and Kurdish both collapse cleanly to a one/other split. Arabic grammatically has six plural
categories (zero/one/two/few/many/other) — full correctness would need a CLDR plural-rule library
(another dependency, ICU-shaped). **Decision: ship the two-form convention for all three locales in
v1**, i.e. Arabic UI plurals will use `_one`/`_other` only, which is linguistically imprecise for
counts of 3–10 and 11+ in Arabic but is a **known, bounded, documented simplification** rather than a
silent gap. This is flagged as Open Question 2 for the Arabic native reviewer (S7.6) to accept,
push back on, or hand-author around (Arabic UI text can often dodge the grammar issue by rewording,
e.g. "٣ عناصر" patterns chosen by the translator rather than the plural engine). Given the actual
string inventory (§0) contains very few count-bearing UI strings (status bar word/character counts
being the main one), the blast radius of the simplification is small.

**Missing-key behaviour — loud to developers/QA, never silently English, never a raw key shown to a writer.**
- In `NODE_ENV !== 'production'` (dev, and the Playwright/unit test harness): `t()` returns a
  **visually distinct sentinel** — `⟦missing:<key>⟧` — and pushes the key onto
  `Rga.I18n.missingKeys()` and `console.error`s it. This satisfies "never a silent English fallback
  that hides gaps" from the masterplan's S7.1 Step 1 verbatim, and gives the S7.4 guard test and the
  S7.5/S7.6 coverage-walk test something machine-checkable to assert zero of.
- In production builds: same sentinel, no console spam expected (because the guard test in S7.4/S7.6
  should make a missing key unshippable), but the sentinel is the safety net if one slips through —
  a visibly broken string is a bug report; silent English is a bug nobody files.
- **English is authored as a real catalogue** (`en.json`), not a fallback source — per the masterplan
  S7.4 Step 1 note. This means `en.json` is subject to the exact same coverage-walk requirement as
  `ku.json`/`ar.json` in principle (RTL-19's guard covers it); it just doesn't need a *native
  reviewer* sign-off since the product is authored in English already.

**Rejected alternative for missing-key handling:** silently rendering the English string when a
locale's key is absent. This is the single most tempting shortcut and the masterplan explicitly bans
it — a partially-translated Kurdish UI that quietly reads as fluent, half-English is worse than one
that visibly screams a placeholder, because the gap becomes invisible to both the developer and the
native reviewer doing the coverage walk.

**Settings-registry labels/descriptions — data, not markup, resolved at render time.**
The registry (`settings-registry.js`) keeps `label`/`description` as plain English strings **as
authored today** — that is the canonical source text S7.4 Step 2 extracts from to seed
`en.json`'s `settings.*` keys (one extraction pass, not a hand-retype). After extraction,
`settings-workspace.js`'s row renderer (`_buildRow`, `renderer/js/shell/workspaces/settings-workspace.js:885+`)
stops reading `entry.label`/`entry.description` directly and instead resolves
`Rga.I18n.t('settings.' + entry.id + '.label')` / `'.description'` at render time. The registry
entry's inline strings remain in the source as the documented **origin** of each key (a comment, not
a live value) so a future contributor adding a new setting knows to add both the entry *and* the
catalogue keys — this is the S7.4 guard test's job to enforce (a registry entry with no matching
`settings.<id>.label` key in `en.json` should fail the guard).

## 3. String extraction strategy

**No big-bang rewrite. Order: highest-visibility chrome first, registry data second, static markup
last** — each is independently shippable and independently diff-reviewable.

1. **Shell JS modules** (`renderer/js/shell/**`, plus the framework modules that render chrome
   copy — `tab-manager.js`, `print-renderer.js` header/footer labels, `review-bar.js`,
   `scene-navigator.js` non-content chrome, `tags.js` panel chrome). Each `textContent = '<literal>'`
   becomes `textContent = Rga.I18n.t('<key>')`. This is the highest-value, most-visible surface (menu
   items, dialog copy, panel headers) and the one the masterplan's own audit sampled
   (`'Scenes'`, `'Recover unsaved work?'`, `'Page Preview'`).
2. **Settings-registry labels/descriptions** (~62 entries × up to 2 fields) via the render-time
   resolution described in §2. This is mechanical and low-risk (one function, `_buildRow`, changes)
   but high string-count, so it is its own step rather than folded into step 1.
3. **`index.html` static markup** (~42 text nodes by the rough recount in §0) via a `data-i18n="<key>"`
   attribute convention plus a single bootstrap pass, `Rga.I18n.applyStaticMarkup(document)`, run once
   at shell init, that walks `[data-i18n]` elements and sets `.textContent` (or `.setAttribute` for
   `data-i18n-attr="title"`-style cases like tooltips/`aria-label`). This avoids introducing a
   templating engine for what is static, load-time-only markup — the attribute is the whole
   mechanism.

**What a reviewer sees in a diff, per string:** exactly two line-local changes in the same commit —
the literal replaced by a `t()`/`data-i18n` call at the call site, and one new key added to
`en.json`. No file is rewritten wholesale; a PR touching 10 strings is a 20-line diff across two
files, not a rewrite of either.

**Extraction is capped by a guard test from the start of S7.4**, not bolted on afterward: `no-hardcoded-ui-strings.test.js` scans the in-scope file set for new bare `textContent = '...'` (and
`data-i18n`-less static English text patterns in `index.html`) against a **shrinking allowlist** —
files not yet converted are allowlisted explicitly by name; the guard fails if a *new* bare literal
appears in a file already off the allowlist, or if the allowlist itself grows. This gives S7.4 a
ratchet instead of a one-time sweep that can rot the moment someone is in a hurry (the masterplan's
own words for why this guard exists).

## 4. The mirroring strategy

**Scope:** `shell.css`, `settings-workspace.css`, `components.css`, `overlays.css` (per masterplan
S7.3 file list; §0 gives current physical/logical counts for all four).

**The sweep, same method R1 already used for print blocks:** every `left`/`right`/`margin-left` /
`padding-right` / `border-left` / `text-align: left` etc. becomes its logical equivalent
(`inset-inline-start`/`inset-inline-end`, `margin-inline-start/end`, `padding-inline-start/end`,
`border-inline-start/end`, `text-align: start/end`) at the **same magnitude** — this is a mechanical
value-preserving conversion, not a redesign. `border-radius` corners that are asymmetric (rare in
this chrome, worth grepping for during S7.3) become `border-start-start-radius` etc.

**What must NOT mirror, and why — explicit rules, not left to slice-time judgement:**

| Category | Mirror? | Rule |
|---|---|---|
| Chrome layout (sidebar, rail, toolbar, tab bar, panels, dropdowns, modals) | **Yes** | This is the whole point of S7.3; convert to logical, let `dir` flip it. |
| OS-anchored window controls (min/max/close, custom title-bar chrome) | **No — stays physical, commented** | These must track the OS title-bar convention (Windows: right; some Linux DEs: left is a *system* setting, not a UI-language setting) — mirroring them to the app's UI language would put them somewhere the OS itself doesn't put its own chrome. Each physical rule here gets a `/* physical: OS title-bar anchor, do not mirror — RTL-18 exemption */` comment so the S7.3 source guard can allowlist it explicitly rather than silently. |
| Line numbers / drafting-guide line (RTL-CHROME-01) | **Follows DOCUMENT direction, not UI direction** | Already the plan's own verdict (masterplan S7.3 Step 4) — restated here so S7.3 doesn't have to re-derive it. These live inside the editor surface, which is document-direction territory (§1), not chrome. |
| Directional navigation icons (back/forward chevrons, expand/collapse, indent/outdent, breadcrumb separators) | **Yes** | Their meaning is relative to reading direction; not mirroring them points them the wrong way in an RTL UI. |
| Fixed-semantic icons (save/disk, trash, gear/settings, search/magnifier, user/avatar) | **No** | Their meaning is an object, not a direction; mirroring a disk icon is meaningless and a magnifier's handle flipping side reads as a rendering bug, not localisation. |
| Media/transport controls (play triangle, seek) | **No** | Platform convention (every OS, every player) keeps play pointing the same way regardless of UI language; mirroring it would be the actual bug here, contrary to naive "mirror everything" instinct. |
| Progress bars / loading fills / scrubbers | **Yes — fill runs start-to-end** | Consistent with logical-property conversion; a progress fill is directional layout, not a fixed icon. |
| Checkmarks, chip/badge shapes, brand mark | **No** | Fixed-semantic, same reasoning as the icon row above. |

This table is the artifact S7.3 needs to stop treating each icon as a one-off judgement call; where
a genuinely ambiguous icon turns up during the sweep that isn't covered by a row above, it becomes a
one-line addition to this table (amend this document), not a silent choice.

**Source guard (S7.3 Step 3):** a grep-based test failing when a new bare `left:`/`right:` (or
`margin-left`/`padding-right`/etc.) appears in the four chrome CSS files **without** an adjacent
`/* physical: <reason> */` comment on the same or preceding line. Same shape as the S7.4 string
guard — a ratchet, not a one-time pass.

## 5. Settings integration

**The applicator (S7.2):** `register('language', function(value) { document.documentElement.setAttribute('dir', DIR_BY_LOCALE[value]); document.documentElement.setAttribute('lang', value); })`
registered in `renderer/js/shell/shell-applicators.js` alongside the existing 14. Per the masterplan
S7.2 Step 1, this applicator does **only** that — direction + lang attribute — nothing about
translation. That keeps S7.2 (direction/mirroring, deliverable and testable in English) cleanly
separable from S7.4 (translation), matching the masterplan's own ordering rationale (§ Phase 7 intro:
"direction-first, translation-second").

**`restartRequired` — recommend flipping `false`, a deliberate reversal of the registry's current
declared value, per the masterplan's explicit instruction to "confirm or change it deliberately."**
- *Rationale:* the Settings Constitution (project doctrine) mandates immediate apply, no Save
  button, for every wired setting; `restartRequired: true` is the one documented escape hatch and
  should be reserved for settings that truly cannot apply live (none currently registered use it —
  `restartRequired` defaults to `false` for all 61 other entries; `language` is the *only* entry
  currently marked `true`, and it was marked that way before any applicator existed, i.e. as a
  placeholder for "this isn't wired, don't pretend it's live" rather than as an architectural claim
  that direction/translation *can't* apply live). Once an applicator exists, direction flip is a pure
  CSS reflow (cheap, instant) and translation swap is a catalogue pointer swap plus a re-render pass
  — both are live-applicable.
- *What live-apply requires that restart would have hidden:* any shell module that renders a string
  once at construction time and caches it in a closure (rather than re-reading `t()` on every render)
  will go stale on a live language change until the user navigates away and back. **S7.4 must ship a
  `localechange` event** (already in the §2 API surface) and an explicit inventory, at S7.4 Step 2
  time, of which shell modules need a re-render subscription vs which already re-render from state
  on every paint (most of `settings-workspace.js`'s row rendering already does, per its existing
  per-row Store subscription pattern noted at `settings-workspace.js:27-29`). This is bounded,
  known-shape work, not a new unknown — flag modules that don't subscribe as a follow-up gap if any
  turn up, don't silently leave them stale.
- *Rejected alternative:* keep `restartRequired: true` and defer this question. Rejected because the
  masterplan explicitly asks S7.1 to decide it, and because keeping it `true` without a technical
  reason would be the one setting in this app's entire registry with a Save-button-shaped affordance
  in a codebase whose constitution forbids Save buttons — that inconsistency would itself need
  justifying later.

**How the choice reaches the DOM, end to end:** Settings row UI (already generic, `settings-workspace.js`)
→ `Store.set('language', 'ku')` (existing generic path, no change) → registered applicator fires
(new, S7.2) → `documentElement.dir/lang` updates (S7.2) and, once S7.4 ships, `Rga.I18n.setLocale('ku')`
fires and emits `localechange` → subscribed modules re-render their cached strings (S7.4). No new
persistence mechanism — this rides the existing tiered Store/applicator infrastructure exactly as
every other wired setting does.

## 6. How RTL-16…RTL-21 get proven

Per the standing rule (Playwright DOM/geometry over screenshots), every row below is a **measurable**
assertion, not a visual spot-check, mirroring the shape S4.1 gave Phase 4.

**RTL-16 — setting is wired.**
`tests/e2e/localisation/ui-direction.spec.js`:
- Open Settings, locate the `language` row; assert it does **not** carry `is-persists-only` (DOM
  class absent) and its description text does **not** end in "Behavior not wired yet." — i.e. assert
  the *absence* of the honest-failure markers the Settings Constitution mandates for unwired rows.
- Change the control to `ku`; assert `Rga.Settings.Applicators.registered()` includes `'language'`.
- Reload the renderer (simulated restart via Playwright page reload against the persisted Store,
  since a full Electron relaunch isn't available to the test harness — this is a known harness
  limitation, not a shortcut; the persisted value round-tripping through the Store's existing
  persistence layer is what's actually being proven) and assert the value is still `ku`.

**RTL-17 — direction is independent of document direction.**
Same spec file, four cases: {UI=en, UI=ku} × {open doc = LTR fixture, open doc = RTL fixture}. For
each: assert `getComputedStyle(document.documentElement).direction` matches the UI setting, **and**
assert the open document's own direction-bearing element (the one from the five sites in §0) still
computes the direction dictated by its *script profile*, unaffected by the UI setting. Reuse existing
fixtures already in `tests/fixtures/` (do not create or edit `.rga` fixtures per standing rule) —
an English-profile fixture and `mysterious-guest-rtl.rga` (RTL profile) give the two document cases;
combine each with both UI languages for the 2×2. Regression target: RTL script inside an English UI
must render with the exact geometry S4.2 measured (cite that spec/baseline by name in the S7.2
implementation so a failure here reads as a *regression against a known-good number*, not a fresh
investigation).

**RTL-18 — chrome mirrors.**
`tests/e2e/localisation/chrome-mirror.spec.js`:
- At UI=en and UI=ku, capture `getBoundingClientRect()` for: sidebar, activity rail, toolbar, tab
  bar, each open panel, the Settings workspace, one open dropdown, one open modal. Assert positions
  mirror around the viewport's vertical center axis (an element at `x` from the left in LTR sits at
  `viewportWidth - x - width` from the left in RTL) while widths/heights are unchanged.
- Assert no two chrome regions' rects intersect in either direction (nothing overlaps).
- Assert every chrome rect's `right` ≤ `viewportWidth` and `left` ≥ 0 in both directions (nothing
  escapes the viewport).
- RTL-CHROME-01 verdict recorded inline: line numbers / drafting-guide line assertions target the
  *document's* direction, not the UI's — a dedicated case proving they do NOT move when only UI
  direction flips (document direction held constant).
- Source guard as a plain Node/grep-based unit test (not Playwright — this one doesn't need a
  browser): scans the four chrome CSS files for un-commented physical `left`/`right`-family
  properties per the §4 table, failing the build on any new one.

**RTL-19 — translation layer exists.**
`tests/unit/shell/i18n.test.js`: `t()` resolves a known key; unknown key returns the sentinel and is
recorded in `missingKeys()`; `{param}` interpolation substitutes correctly; `_one`/`_other` selection
picks the right form for count 1 vs other counts. `tests/unit/shell/no-hardcoded-ui-strings.test.js`:
the extraction guard from §3, run against the full in-scope file list, zero violations outside the
(shrinking, explicit) allowlist.

**RTL-20 / RTL-21 — translations complete and reviewed.**
A coverage test (`tests/unit/shell/i18n.test.js` or a sibling) diffs `ku.json`/`ar.json` key sets
against `en.json` (the canonical key set) and asserts **zero missing and zero extra keys** — this is
the "full catalogue coverage (no missing-key fallbacks in a walk of every surface)" criterion made
machine-checkable. Translation *correctness* (is the Kurdish actually good Kurdish) is explicitly
**not** machine-testable and stays a human step: the native reviewer's name + sign-off date recorded
in the S7.5/S7.6 evidence file, plus a screenshot walk of the main surfaces in that language, exactly
as the masterplan's S7.5/S7.6 step lists already specify. This brief does not invent a way around
that human step — per the masterplan's own citation of START rule 6, a person is outside an agent's
power, and no test can substitute for one here.

## §9 Rulings on the open questions (orchestrator + user, 2026-07-29)

Three of the six were decidable from existing project doctrine and are **settled here so S7.2 is not
blocked on them**. Three genuinely need the user and stay open.

### ✅ Q4 — `language.restartRequired` flips `true` → `false` (live apply). SETTLED.
The Settings Constitution is explicit: **immediate apply, no Save button**; a setting that demands a
restart is a worse citizen than one that re-renders. The brief's own `localechange` re-render event
(owned by S7.4) is what makes this affordable. **S7.2 must ship `restartRequired: false`.** A restart
prompt for changing interface language would also read as an admission that the layer is not really
live — precisely the impression Phase 7 exists to remove.

### ✅ Q2 — two-form plurals (`_one` / `_other`) are ACCEPTED for v1. SETTLED, with a condition.
Arabic has six CLDR plural categories and Kurdish (Sorani) two; a two-form simplification is
genuinely lossy for Arabic. It is accepted for v1 **only because the UI surface is ~60–100 mostly
non-counting strings**, so the blast radius is a handful of phrases. **Conditions:** (a) the lookup
API must be shaped so full CLDR categories can be added later *without* touching call sites — the
call site says "plural", the layer decides how many forms; (b) any string that would be visibly wrong
in Arabic under two forms must be **rewritten to avoid the count** (a standard, honest i18n move)
rather than shipped wrong; (c) the native reviewers at S7.5/S7.6 are explicitly asked to flag plural
phrasing. Recorded so a later agent does not read "two forms" as "Arabic plurals are handled".

### ✅ Q6 — a real relaunch check IS required; append it to S7.7. SETTLED.
A Store round-trip plus page reload is a fine *standing automated* guard and should stay in the
suite — but it does not prove what RTL-16 claims ("survives restart"), because it never exercises a
real Electron process start. This project has an established pattern for exactly this gap: the
physical checks in S2.2 (installer smoke) and S3.1 (post-reboot launch) were **user-performed and
recorded as evidence**. Same here: **S7.7's full-app walk must include "quit the app completely,
relaunch, confirm the interface language and direction persisted"**, recorded in its evidence file.
Doctrine forbids mocking past a physical gate; this keeps the automated guard honest about its scope
instead of letting it overclaim.

### ⏳ Still open — these need the user
- **Q1 — a named Kurdish (Sorani) native reviewer for S7.5.** The phase's long-lead external
  dependency and the one most likely to become the final blocker. Outstanding since 2026-07-28.
- **Q3 — does Arabic ship at launch (P0), or move to P1 if no reviewer is found?** A scope decision,
  not a technical one. Note the asymmetry: Kurdish is the product's reason for existing, Arabic is
  reach. RTL-21 is currently a launch-blocking P0, so if the answer is "P1", **the checklist must be
  amended to say so** rather than the row quietly failing at S6.1.
- **Q5 — vendor a UI-weight Arabic/Kurdish font for the chrome, or accept OS fallback for v1?**
  New finding from this slice: `--font-ui` has no Arabic-script member, and the vendored Arabic fonts
  are wired for *document* text only. So today a Kurdish UI would render in whatever the OS supplies.
  Not blocking S7.2–S7.4; **must be answered before S7.5/S7.6** or the native reviewers will be
  judging typography that is not the shipping typography.
