# S2.4F — GAP-2-3 fix: Page Setup's paper-size dropdown actually changes the paper size

Date: 2026-07-29
HEAD SHA at slice start: `0ed5f5b25a32cd5fe911fdb08d8e578272c56d32`

## Symptom

Page Setup (Ctrl+Shift+G) → choose a different Paper size → Apply. Nothing happens: the paper size
never changes, for any user, in either script direction. No error, no toast — silent no-op.

## Step 1 — reproduce as a failing test first (TDD)

Wrote `rwanga-editor/tests/e2e/settings/page-setup-paper-size.spec.js` against the pre-fix code and
ran it foreground/blocking:

- Test "choosing A4 in Page Setup and clicking Apply resizes the Flow page to 1122.52px" — could not
  even complete: `page.locator('#ps-paper').selectOption('a4')` timed out because the pre-fix
  `<option>` values were `'Letter'`/`'A4'`/`'Legal'` (capitalized, sourced from
  `Rga.Constants.PAPER_SIZES` keys) — there was no lowercase `'a4'` option to select at all.
- Test "switching A4 -> Letter and back" — same failure.
- Test "every Page Setup paper-size option is registry-legal" (the class guard) — failed for a
  different, deeper reason once the option-value bug was worked around: the dropdown's values were
  `['Letter','A4','Legal']`, the registry's accepted values are `['letter','a4','custom']` — **zero
  overlap**, confirming every option in the control was invalid.

All 3 red, confirmed by running the file directly (not merely reasoning about the code).

## Step 2 — root cause and which end was fixed

**Root cause**, exactly as flagged in S2.3F's incidental discovery:

- `rwanga-editor/renderer/js/editor/page-setup-dialog.js:18-21` (`_paperSizeNames()`, pre-fix) built
  the `<select>` options from `Rga.Constants.PAPER_SIZES` keys: `'Letter'`, `'A4'`, `'Legal'`.
- `rwanga-editor/renderer/js/shell/settings-registry.js:283-291` (`pageSetup.paperSize` entry) accepts
  only lowercase `options: ['letter', 'a4', 'custom']`.
- `rwanga-editor/renderer/js/shell/settings-validators.js:27-30` (`select(v, options)`) does a
  case-sensitive `options.indexOf(v)`. `'A4'` never matches `'a4'`, so every Apply's
  `Store.set('pageSetup.paperSize', paper.value)` silently returns `false` (a `console.warn`, no
  exception, no UI feedback) — the doc's paper size never changes.
- A second, independent instance of the same bug CLASS, found while building the class-guard test:
  `'Legal'` was never a registry-accepted value either (the registry has no `legal` option at all),
  so even fixing only the casing would have left "Legal" silently broken too.

**Which end was fixed, and why:** the CONTROL, not the registry. `rwanga-editor/renderer/js/framework
/layout-profile.js:283-288` already documents a precedent (S8) that the registry's lowercase form is
canonical and read-side consumers normalize case at the boundary when resolving paper dimensions.
Per the Settings Architecture Doctrine (registry = SSOT for what a setting accepts), the control
should emit only values the registry accepts — not the reverse. Loosening the registry's validator
to accept both cases would let a SECOND, differently-cased writer of `pageSetup.paperSize` reappear
later and pass a case-sensitive read elsewhere; keeping ONE canonical form (the registry's lowercase
options) and fixing the boundary that emits a mismatched form is the doctrine-preferred shape
("prefer ONE canonical form with normalisation at the boundary rather than sprinkling `.toLowerCase()`
at call sites").

**Fix**, in `rwanga-editor/renderer/js/editor/page-setup-dialog.js`:

1. `_paperSizeNames()` replaced by `_paperSizeOptions()`, which reads
   `Rga.Settings.Registry.get('pageSetup.paperSize').options` (the canonical lowercase list) and
   `.labels` (for display text), and intersects the options list, case-insensitively, with
   `Rga.Constants.PAPER_SIZES` (the only table with real paper dimensions). This yields exactly
   `['letter', 'a4']` today: `'custom'` is dropped (registry-legal but no dims table entry and no
   custom-size UI in this modal — inventing that is out of GAP-2-3's scope) and `'Legal'` is dropped
   (has dims but was never registry-legal — a pre-existing, separate mismatch this fix also resolves
   by omission rather than by newly wiring Legal support).
2. The `<option value="...">` now carries the registry's lowercase value directly; the display label
   comes from the registry's `labels` map ("US Letter", "A4").
3. The seed line (`paper.value = ps.paperSize`) now lowercases before assignment
   (`ps.paperSize.toLowerCase()`), because `doc.settings.pageSetup.paperSize` may still be stored
   capitalized (`doc.js:78`'s new-doc default is `'Letter'`) while the `<option>` values are now
   lowercase — without this, the `<select>` would silently fail to pre-select the current size on
   open (a seeding bug, not an Apply bug, but part of the same seam).
4. The Apply handler itself (`Store.set('pageSetup.paperSize', paper.value)`) is UNCHANGED —
   `paper.value` is now already the canonical lowercase form, so no normalisation is needed at the
   call site. This is the "fix at the boundary, not sprinkled" shape.

## Step 3 — the class guard

New test `page-setup-paper-size.spec.js`: "GAP-2-3 class guard — every Page Setup paper-size option
is registry-legal" opens the real modal, reads every `<option value>` from `#ps-paper`, and asserts
each one is a member of `Rga.Settings.Registry.get('pageSetup.paperSize').options`. This is the
general form of the bug (control emits a value the registry's SSOT contract does not accept) and
will catch a recurrence of this exact class the next time a Page Setup control's option set drifts
from the registry, at test time rather than by a silent no-op in the shipped app.

driving the REAL modal (`Rga.PageSetup.open` with the real `onApply` callback that calls

Ctrl+Shift+G) — not a Store-only check.

the effective value actually changed, not merely that a handler fired.
