### Observation (not a failure): "V.O."-style trailing period

Raw boundary-character measurement (i.e. comparing the very first and very last *byte* of the literal
run string `"V.O."`, not its first/last alphanumeric character) shows the **trailing** period
detaching from the `V…O` run and sitting adjacent to the following `)` instead — e.g. for `ئەدیب
(V.O.)`: `(`=1035.6, `V`=1006.9–1017.9, first `.`=1017.9–1022.4, `O`=1022.4–1035.6, second
`.`=1002.5–1006.9, `)`=998.0–1002.5. Visual left→right order is `) . V . O (` — the closing paren and
its adjacent period correctly mirror to the left (reading-end), and `V . O` (the letters plus the
*internal* period between them) render left-to-right as a coherent unit; only the **final** period —
which sits directly against the closing paren — gets pulled toward the RTL/neutral cluster on its
other side. This is standard UAX#9 weak/neutral-character resolution (Rule N1/N2) for a punctuation
mark wedged between an LTR run and a closing bracket that opens onto RTL context, not a
base-direction bug — the protocol's FAIL signature for RTL-12 is "a whole line jumping to LTR
alignment," which did not happen here. Recorded (`rawBoundaryObservation` in the JSON evidence) for
visibility, not asserted, and not counted against the verdict. Seen on all three `(V.O.)`/`(VOICEOVER،
OFF)` character-cue samples (#1, #9, #11, #13).

## Spec notes for a later reader

- `measureLine()` in the spec walks the block's live **text nodes** (not `el.textContent` alone) to
  build `Range`s for arbitrary substrings, so it is robust to any inline tag/entity `<span>` a future
  change might introduce inside a block.
- The Print-surface search deliberately does **not** scope by `.rga-page-sheet-content` (there are 85
  of them, one per page) — an early version of this spec used `document.querySelector` (singular) and
  silently only ever searched page 1, producing false "block not found" failures for scenes past page
  1. Fixed to search the whole `document` (the `.rga-block-*` / `.rga-print-block-*` prefixes never
  collide between Flow and Print).
- Latin-run ordering is checked on the run's first/last **alphanumeric** character, not its literal
  string's first/last byte — see the "V.O." observation above for why the literal-boundary check would
  have produced a false red that isn't the base-direction bug the protocol is hunting for.

- **Ordering flake found and fixed during orchestrator verification (2026-07-29).** The spec was
  green when RTL-13 ran alone but failed `Flow: battery line "period" not found after typing` when the
  file ran in order. Cause: `closePreview()` ended in a fixed `waitForTimeout(150)` and asserted
  nothing, so RTL-12 could hand over a still-active Print Preview overlaying the editor — RTL-13's
  clicks and keystrokes then landed nowhere. Fixed by waiting on real state
  (`PrintPreview.isActive() === false` **and** an editor with non-zero geometry), plus a
  `waitForFunction` after the typing loop asserting every battery line actually reached the document,
  so a future focus/overlay problem fails as itself instead of masquerading as a bidi measurement
  failure. No assertion was weakened. Full file green on two consecutive back-to-back runs.
